# 14 MCP 协议基础与架构原理

## 什么是 MCP（Model Context Protocol）？

MCP 是 Anthropic 于 2024 年底开源的一套开放协议标准，被称为 **“AI 应用时代的 USB-C 接口”**。

在 MCP 出现之前：
- 每一个 Agent 框架（LangChain, AutoGen, 自研系统）都要自己定义一套 `Tool` 接口。
- 每一个外部工具（GitHub、Postgres、Slack）都要为不同的框架重复写一次适配代码。

MCP 出现之后：
- 工具提供方只需编写一个 **MCP Server**。
- 任何支持 MCP 的客户端（Cursor、Claude Desktop、你的 Go Agent）都可以**直接即插即用**连接并使用该工具。

## 核心架构：三层角色分工

```text
+-------------------------------------------------------------------------------+
|                               MCP 整体架构图                                   |
+-------------------------------------------------------------------------------+

+-------------------------------------------------------------------------------+
| Host (宿主环境，如 Cursor / Claude Desktop / 自研 Agent)                      |
|                                                                               |
|   +--------------------------+          +---------------------------------+   |
|   | LLM 模型推理             |          | MCP Client                      |   |
|   | (理解语义并决策 ToolCall)|<-------->| (负责建立连接、发 RPC、解包结果)|   |
|   +--------------------------+          +----------------+----------------+   |
+----------------------------------------------------------|--------------------+
                                                           |
                                  JSON-RPC 2.0 协议通道    | (stdio / SSE / HTTP)
                                                           |
                                                           v
+-------------------------------------------------------------------------------+
| MCP Server (工具提供方，独立进程 / 微服务，如用 Go 实现的 04-mcp)              |
|                                                                               |
|   1. 握手能力协商:   initialize / notifications/initialized                   |
|   2. 工具目录发现:   tools/list (向 Client 返回工具的 JSON Schema)            |
|   3. 工具具体执行:   tools/call (接收参数 -> 本地计算 -> 返回内容)            |
+-------------------------------------------------------------------------------+
```

---

## MCP 协议的核心通信交互流程（时序）

MCP 协议基于标准的 **JSON-RPC 2.0** 格式，典型握手与调用过程包括 3 个阶段：

```text
Client (Host)                                           Server (Go MCP Server)
      |                                                           |
      | 1. Request: {"method":"initialize", "params":{...}}       |
      |---------------------------------------------------------->|
      | 2. Response: {"result":{"capabilities":{"tools":{...}}}}  |
      | (服务端声明支持 tools 功能及版本)                         |
      |<----------------------------------------------------------|
      |                                                           |
      | 3. Notification: {"method":"notifications/initialized"}   |
      | (握手完成确认)                                            |
      |---------------------------------------------------------->|
      |                                                           |
      | 4. Request: {"method":"tools/list"}                       |
      |---------------------------------------------------------->|
      | 5. Response: {"result":{"tools":[{"name":"calculator"...}]}}|
      | (向客户端暴露所有可用工具定义及 Schema)                   |
      |<----------------------------------------------------------|
      |                                                           |
      | 6. Request: {"method":"tools/call", "params":{"name":"calculator","arguments":{"left_operand":10,"right_operand":20,"operation":"add"}}}
      |---------------------------------------------------------->|
      | 7. Response: {"result":{"content":[{"type":"text","text":"30"}]}}
      | (服务端执行完毕，返回标准 Content 格式)                  |
      |<----------------------------------------------------------|
```

---

## 阶段 3（内部 Function Calling） vs 阶段 4（MCP 协议化）

| 维度 | 阶段 3（内部 ToolCalling） | 阶段 4（MCP 协议） |
|---|---|---|
| **耦合度** | 工具代码硬编码在同一个 Go 进程内 | 独立进程/独立网络服务，解耦 |
| **复用性** | 只能给当前项目用 | 任何支持 MCP 的宿主（Cursor/Claude）直接通用 |
| **权限与安全** | 工具和主程序同权限同生命周期 | 进程隔离，可以分配独立沙箱与资源配额 |
| **通信方式** | 进程内内存函数调用 | 标准 JSON-RPC 2.0（stdio / HTTP+SSE） |
