# Prompt 工程基础：把模型输入设计成可控协议

## Prompt 不只是“提示词”

在 LLM 应用里，Prompt 更像一份输入协议。它告诉模型：

- 你是谁：角色和能力边界
- 要做什么：任务目标
- 根据什么做：上下文资料
- 怎么输出：格式、字段、语言、长度
- 不该做什么：禁止编造、禁止输出 Markdown、没有答案就说不知道

Prompt 写得随意，模型输出就更像聊天；Prompt 写得清楚，模型输出才更像业务系统可以消费的结果。

## Prompt 的常见组成

一个工程化 Prompt 通常包含这些部分：

```text
角色：你是一个严格的 JSON 生成器
任务：把用户给的主题整理成学习卡片
上下文：下面是可参考资料
输出格式：只返回 JSON，字段必须包含 title、summary、keywords
约束：不要返回 Markdown；上下文没有答案就说不知道
用户输入：RAG 是什么
```

不是每次都要写满这些部分，但业务越要求稳定，Prompt 越要明确。

## 本项目里的三个例子

### 1. 普通聊天 Prompt

位置：`01-llm-basics/main.go`

```go
Content: "你是一个简洁、专业的 Go 编程助手，回答时优先给出代码示例。"
```

这个 Prompt 主要控制角色和回答风格。它比较宽松，所以适合普通聊天。

### 2. 结构化输出 Prompt

位置：`01-llm-basics/main.go`

```text
你是一个严格的 JSON 生成器。只返回 JSON，不要返回 Markdown，不要返回代码块。
JSON 必须包含这些字段：
{
  "title": "string",
  "summary": "string",
  "keywords": ["string"],
  "difficulty": "beginner|intermediate|advanced",
  "next_action": "string"
}
```

这个 Prompt 比普通聊天强很多，因为它明确规定了输出格式。即便如此，模型仍可能返回非法 JSON，所以 Go 代码还必须用 `json.Unmarshal` 校验，不能只相信 Prompt。

### 3. RAG Prompt

位置：`02-rag/main.go`

```text
请只根据下面的上下文回答问题；如果上下文没有答案，就说不知道。

上下文:
[1] 来源: ...
标题: ...
内容: ...

问题: ...
```

这个 Prompt 的重点是约束模型“只基于检索上下文回答”。这是 RAG 防幻觉的核心手段之一，但它不能替代检索质量。如果检索到的 chunk 错了，Prompt 再好也救不了全部问题。

## Prompt 和代码的关系

Prompt 负责提高模型输出稳定性，但代码负责兜底：

| 问题 | Prompt 做什么 | 代码做什么 |
|---|---|---|
| 输出格式不稳定 | 要求只返回 JSON | 解析失败就报错或重试 |
| 模型编造答案 | 要求只基于上下文 | 检查是否有检索结果和来源 |
| 输出太长 | 要求简洁 | 设置 `max_tokens` |
| 响应太慢 | 无法可靠解决 | 设置 timeout |
| 答案不可追溯 | 要求输出来源 | 保存 source、title、chunk index |

工程结论：

> Prompt 是第一层约束，代码校验是最后一道防线。真实业务不能只靠 Prompt 保证正确性。

## 面试表达

如果面试官问“你怎么设计 Prompt”，可以这样回答：

> 我会把 Prompt 当成模型输入协议来设计，而不是简单写一句提示。通常会明确角色、任务、上下文、输出格式和禁止事项。比如 RAG 场景中，我会要求模型只基于检索上下文回答、没有答案就说不知道，并要求返回来源。但我不会只依赖 Prompt，代码侧还会做 JSON 解析、字段校验、超时控制和错误处理。

## 当前重点

- Prompt 决定模型如何理解任务
- Prompt 越具体，输出通常越稳定
- Prompt 不能替代代码校验
- RAG Prompt 的核心是“只基于上下文回答”
- 结构化输出 Prompt 的核心是“规定字段和格式”
