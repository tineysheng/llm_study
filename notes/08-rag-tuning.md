# 08 RAG 调优与面试准备

## 本课目标

前面已经完成了最小 RAG 闭环：

```text
用户问题 -> query embedding -> Top-K 检索 -> Prompt 拼接 -> 基于上下文回答 -> 输出来源
```

这一课不急着接真实向量数据库，而是学习真实项目里更常见的问题：**RAG 效果不好时，应该看哪里、调什么、怎么向面试官解释**。

本课重点：

- 调整 `Top-K`，观察召回和噪声变化
- 调整 `threshold`，观察回答和拒答变化
- 对比不同 `chunk size` 的效果
- 对比“无 RAG 直接问”和“有 RAG 问”的差异
- 总结 RAG 常见问题：召回失败、上下文污染、幻觉、引用错误

## 本课必须先懂的术语

### 1. RAG Tuning（RAG 调优）

RAG 调优不是让模型“更聪明”这么简单，而是优化整个链路：

```text
文档切分 -> 向量化 -> 检索 -> 上下文拼接 -> 模型生成 -> 引用来源 -> 效果评估
```

如果最终答案不好，原因可能在任何一步，而不一定是 Chat Model 不行。

### 2. Recall Failure（召回失败）

召回失败指：知识库里明明有答案，但检索阶段没有把正确 chunk 找出来。

例子：

```text
问题：怎么设置 OpenAI API Key？
正确 chunk：API Key 配置
实际 Top-K：Streaming 流式输出、JSON 结构化输出
```

这时模型即使很强，也看不到正确资料，最终答案很可能不可靠。

常见原因：

- chunk 切得太碎，关键信息分散
- chunk 切得太大，向量主题被稀释
- Embedding 模型不适合当前语言或领域
- 用户问题表达和文档表达差异太大
- Top-K 太小，正确 chunk 排在后面没被取到

### 3. Context Pollution（上下文污染）

上下文污染指：Top-K 里混入了弱相关或无关 chunk，并被一起放进 Prompt。

风险：

- 增加 token 成本和延迟
- 干扰模型判断
- 让模型引用不该引用的来源
- 在答案里混入无关内容

Top-K 越大，召回更多，但上下文污染风险也越高。

### 4. Score Threshold（相似度阈值）

`threshold` 是最低相关性要求。

```text
Top-1 score >= threshold -> 可以回答
Top-1 score < threshold  -> 应该说不知道
```

阈值太低：系统更愿意回答，但容易基于不相关上下文硬答。

阈值太高：系统更谨慎，但可能把本来能回答的问题也拒答。

### 5. Citation Error（引用错误）

引用错误指答案后面的来源和实际依据不一致。

例子：

```text
答案讲 API Key 配置，但引用来源却是 Streaming 流式输出章节。
```

真实项目里，引用错误会严重影响用户信任，也会让问题排查变困难。

### 6. Evaluation Set（评测集）

评测集是一组固定问题和期望答案，用来观察调参前后的效果变化。

最小评测集可以包括：

- 知识库内能回答的问题
- 知识库外不能回答的问题
- 表达方式不同但语义相同的问题
- 容易检索到相邻主题的问题

没有评测集，只凭感觉调 Top-K 和 chunk size，很容易越调越乱。

## 如何看懂本课输出

### 1. 无 RAG vs 有 RAG

无 RAG 直接回答没有检索本地知识库，也没有引用来源。

有 RAG 回答会先检索 chunk，再基于上下文回答，并输出来源。

你要观察：

- 答案是否来自知识库
- 是否有引用来源
- 知识库外问题是否会说不知道

### 2. Top-K 调优观察

输出里会看到类似：

```text
top-k  top1    chars   noise      titles
1      0.994   47      0          API Key 配置
2      0.994   89      1          API Key 配置 | RAG 和微调的区别
```

字段含义：

- `top-k`：取前几个 chunk
- `top1`：最高相似度分数
- `chars`：拼进上下文的字符数，用来近似观察 token 成本
- `noise`：无关 chunk 数量
- `titles`：本次召回的 chunk 标题

观察重点：

- K 太小：可能漏掉答案
- K 太大：可能带入噪声、增加成本和延迟

### 3. Threshold 调优观察

输出里会看到：

```text
threshold=0.50 -> 回答
threshold=0.75 -> 回答
threshold=0.95 -> 说不知道
```

观察重点：

- 阈值越低，系统越激进
- 阈值越高，系统越保守
- 企业知识库问答通常宁愿说不知道，也不要编造答案

### 4. Chunk Size 调优观察

本课用三种 mock chunk 策略模拟：

| 策略 | 现象 | 风险 |
|---|---|---|
| small | chunk 很短，信息可能被拆散 | Top-1 只拿到半个答案 |
| medium | 信息完整，噪声较少 | 通常是学习阶段最容易理解的策略 |
| large | 一个 chunk 放很多内容 | 成本高，主题混杂，上下文污染 |

真实项目里通常不会只看字符数，而会结合 token 数、标题结构、段落边界、代码块、表格和评测结果。

## RAG 效果不好时的排查顺序

建议按这个顺序排查：

1. **看检索结果**：Top-K 是否包含正确 chunk？
2. **看分数**：Top-1 分数是否明显高于其他 chunk？
3. **看 chunk 内容**：正确 chunk 是否包含完整答案？
4. **看噪声**：Top-K 是否混入太多无关 chunk？
5. **看 Prompt**：是否明确要求只基于上下文回答、无答案说不知道？
6. **看引用**：答案引用是否真的对应上下文？
7. **看评测集**：调参后是整体变好，还是只对某一个问题变好？

## 本课常见误区

### 误区 1：Top-K 越大越好

不一定。Top-K 大可能提高召回，但也会带来更多无关 chunk、更多 token 成本、更高延迟和上下文污染。

### 误区 2：只要换更强的 Chat Model，RAG 就会变好

不一定。如果检索阶段没有召回正确 chunk，强模型也看不到答案。RAG 的上限首先受检索质量影响。

### 误区 3：chunk 越大越安全

不一定。chunk 大能保留更多上下文，但也容易混入多个主题，让 embedding 表示变模糊，并增加 Prompt 噪声。

### 误区 4：相似度高就等于答案正确

不等于。相似度高只说明语义更可能相关，不证明事实正确，也不证明 chunk 里一定包含完整答案。

### 误区 5：引用来源只是展示效果

不是。引用是 RAG 的可信度和可排查性基础。没有引用，用户很难判断答案依据；开发者也很难定位是检索错了还是生成错了。

## 面试表达模板

如果面试官问：“你会怎么优化一个 RAG 系统？”

可以这样回答：

> 我会先建立一组固定评测问题，区分知识库内问题和知识库外问题。然后先看检索结果，确认 Top-K 是否召回正确 chunk；如果召回失败，就检查 chunk 切分、Embedding 模型、Top-K 和查询表达。如果召回到了但回答不好，就检查 Prompt、上下文噪声、threshold 和引用来源。调优时不会只追求 Top-K 变大，因为它会增加 token 成本和上下文污染。线上还需要记录 query、Top-K、score、answer、citation 和用户反馈，用数据持续迭代。

## 当前重点

- RAG 调优要先看检索，再看生成
- Top-K 是召回和噪声的权衡
- threshold 是回答率和错误率的权衡
- chunk size 是上下文完整性、成本和主题纯度的权衡
- 评测集和日志是持续优化 RAG 的基础
