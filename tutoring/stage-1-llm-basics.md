## 第一关学习记录：LLM API 无状态与消息历史

### 本关知识点

LLM API 本身是无状态的。模型不会自动记住上一次对话，应用程序必须在每次请求时把需要的历史消息传给模型。

在本项目 `01-llm-basics/main.go` 中，对话历史由 `messages` 变量维护：

- `system`：约束模型角色和回答风格
- `user`：用户输入
- `assistant`：模型之前的回答

### 本关实现内容

已在 CLI 中加入：

- `/help`：查看命令
- `/history`：查看当前消息历史
- `/reset`：清空历史，但保留 `systemMessage`
- `/exit` 和 `quit`：退出程序

### 本关问答记录

**问题 1：为什么 LLM API 本身是“无状态”的？在这个项目里，程序是靠哪一个变量让模型表现得像“记得之前聊过什么”？**

我的回答：

> 大模型不保存任何东西，只会根据你给他的内容，AI 进行回答。靠 content。

AI 反馈：

> 第一部分答对了：模型不会替应用保存会话状态，只根据本次请求传入的内容生成回答。第二部分需要纠正：负责保存历史的是 `messages` 这个切片，`content` 只是每条消息里的文本字段。

标准答案：

> LLM API 是无状态的，因为服务端不会为我的应用自动保存某个用户的完整对话。每次调用 API 时，模型只看到这一次请求里的 messages。项目中是 `messages` 这个切片保存了 system、user、assistant 消息，所以模型才表现得像记得之前聊过什么。

**问题 2：为什么 `/reset` 不能把 `messages` 变成空切片，而是要保留 `systemMessage`？**

我的回答：

> 变成空切片，下次和 AI 对话就不会带上任何上下文信息了，systemMessage 是这次会话最核心的信息，所以要保留。

AI 反馈：

> 这题答得好。补充一点：`systemMessage` 不只是上下文信息，它还负责约束模型的角色和回答风格；清掉它后模型仍能回答，但行为约束会丢失。

标准答案：

> `/reset` 的目标是清空用户和模型的历史对话，而不是清空整个会话配置。`systemMessage` 定义了模型的角色、语气和行为边界，所以 reset 后仍然要保留它。否则模型还能回答，但不再受原来的系统提示约束。

**问题 3：在当前代码里，每次用户正常提问后，为什么要把 assistant 的完整回复 append 回 `messages`？如果不 append，会发生什么？**

我的回答：

> 这样会有个问题，让 AI 缺失了一些上下文，下次 AI 回答就不够准确。

AI 反馈：

> 回答正确。更完整地说：如果不把 assistant 回复写回 `messages`，下一轮模型只能看到用户说过什么，看不到自己上一轮回答过什么。这样连续对话、追问、纠错和“基于你刚才的回答继续”都会变差。

标准答案：

> 多轮对话不只需要保存用户输入，也需要保存模型之前的回答。因为下一轮用户可能会说“继续”“你刚才那段代码改一下”“为什么这样做”，这些都依赖 assistant 上一轮的输出。如果不 append assistant 回复，模型就缺少自己之前回答的上下文。

## 第二关学习记录：模型参数控制

### 本关知识点

模型参数决定 LLM 应用的能力、成本、稳定性和响应速度。本关学习：

- `model`：选择模型
- `temperature`：控制输出确定性和发散程度
- `max_tokens`：控制输出长度、成本和失控风险
- `timeout`：避免请求外部 API 时长时间卡住

### 本关实现内容

已在 `01-llm-basics/main.go` 中加入：

- 命令行参数配置：`-model`、`-temperature`、`-max-tokens`、`-timeout-seconds`
- `/config` 命令：查看当前配置
- `context.WithTimeout`：为每次 API 请求增加超时

### 本关问答记录

**问题 1：如果你要让模型回答更稳定、更适合写代码，temperature 应该调高还是调低？为什么？**

我的回答：

> 调低，temperature 低，回答问题比较保守适合写代码。如果是高适合创建新东西，适合设计新东西，例如产品设计等。

AI 反馈：

> 答得很好。写代码、事实问答、结构化抽取通常要低 temperature；创意、头脑风暴、产品方案可以适当调高。补充一点：temperature 低不代表绝对每次一样，只是随机性更低。

标准答案：

> 写代码通常应该调低 temperature，因为代码任务更重视稳定、准确和可复现。temperature 越高，模型越容易给出发散、多样但不稳定的回答，更适合创意类任务。

**问题 2：`max_tokens` 控制的是输入长度、输出长度，还是整个上下文窗口？如果把它设置得很小，可能会发生什么？**

我的回答：

> 输出长度，设置太小，AI 回答可能会不完整？

AI 反馈：

> 正确。`max_tokens` 主要限制模型这次最多能生成多少输出 token；设置太小会导致回答变短、信息缺失，甚至代码或 JSON 被截断。

标准答案：

> `max_tokens` 控制的是本次请求的最大输出长度，不是输入长度，也不是整个上下文窗口。设置太小会导致回答不完整、代码被截断、JSON 不合法或关键信息缺失。

**问题 3：为什么后端服务调用 LLM API 时要设置 timeout？如果没有 timeout，线上可能出现什么问题？**

我的回答：

> 这个是调用 API 通用的一个问题，要设置超时，因为网络请求其实是不稳定的，可能会由于各种情况会超时，所以如果超时了，我们的服务不应该继续等待，可以直接抛出异常或者重新请求。

AI 反馈：

> 回答正确。timeout 是后端调用外部服务的基本保护。没有 timeout，请求可能长期占用 goroutine、连接、内存等资源，最终导致服务堆积、响应变慢甚至雪崩。

标准答案：

> LLM API 是外部网络调用，可能因为网络抖动、服务拥塞、限流等原因长时间无响应。后端服务必须设置 timeout，避免请求无限等待，占用 goroutine 和连接资源。超时后应该明确返回错误，必要时再结合重试、降级或用户提示。

**补充问题 4：`model` 参数为什么也要做成可配置？在真实项目中，换模型通常会影响哪些方面？**

我的回答：

> 因为可以选择的模型有很多，不同的模型能力差别很大，而且有些模型时间久了忽然又变很强了，还便宜。

AI 反馈：

> 答得方向对：模型能力、价格会变化，所以不能写死。补充完整一些：换模型还会影响速度、上下文窗口、结构化输出能力、工具调用能力、多模态能力、稳定性和兼容性。

标准答案：

> `model` 应该可配置，因为不同模型在能力、成本、速度、上下文窗口、工具调用、结构化输出、多模态和稳定性上都有差异。真实项目中经常需要根据任务复杂度、成本预算和效果要求切换模型。

**补充问题 5：同一个用户问题，如果用便宜的小模型和更强的大模型分别回答，你会从哪些 AI 应用角度判断该用哪个模型？**

我的回答：

> 回答问题的质量、性价比、使用场景等。

AI 反馈：

> 答对方向了，但还可以更工程化。除了质量、性价比、场景，还要看：响应速度、上下文长度、是否支持工具调用/结构化输出、错误率、稳定性、用户是否能接受延迟，以及任务失败的业务代价。

标准答案：

> 判断模型选择时，不只看“强不强”，还要看任务复杂度、答案质量、成本、延迟、上下文长度、结构化输出能力、工具调用能力、稳定性和失败代价。简单任务可以用小模型，复杂推理、关键决策或高失败代价任务更适合强模型。

**补充问题 6：如果一个功能要求模型稳定返回可解析的 JSON，你会倾向于把 temperature 调低还是调高？为什么这和普通聊天不一样？**

我的回答：

> 调低。这个问题之前你问过类似的了，我觉得你应该是第二课能问的已经问完了。

AI 反馈：

> 判断正确。稳定 JSON 输出需要更低随机性，所以倾向低 temperature。同时用户反馈也正确：这个问题和前面的 temperature 问题重复度较高，说明本关已经达到掌握标准，不应该继续机械追问。

标准答案：

> 稳定 JSON 输出通常应降低 temperature，因为结构化输出更重视格式稳定、字段完整和可解析性，不像普通聊天那样追求多样表达。

## 第三关学习记录：结构化输出

### 本关知识点

普通聊天输出适合人读，但业务系统通常需要稳定、可解析、字段明确的数据。结构化输出的目标是让 LLM 返回符合约定结构的数据，例如 JSON，然后由程序解析并继续处理。

本关重点：

- 自然语言输出不稳定，不适合直接作为业务接口
- JSON 可以被 Go 程序解析成结构体
- Prompt 可以约束模型输出字段和格式
- 模型仍可能返回非法 JSON，所以必须处理解析失败

### 本关实现内容

已在 `01-llm-basics/main.go` 中加入：

- `learningCard` 结构体：定义结构化学习卡片
- `/json <主题>` 命令：让模型返回 JSON 学习卡片
- `generateLearningCard`：调用模型生成 JSON，并用 `encoding/json` 解析
- `printLearningCard`：把解析后的结构体打印给用户
- 解析失败时输出错误和模型原始内容，方便定位问题

### 运行方式

```powershell
go run ./01-llm-basics -temperature 0.2
```

进入 CLI 后输入：

```text
/json RAG 是什么
/json Go channel
/json function calling
```

AI 反馈：

> 答得很好，方向完全对。小修正：streaming 展示的是模型逐步生成的文本，不一定等于“真实思考过程”；但它确实改善等待体验，让用户知道系统还在响应，也方便中途停止。
